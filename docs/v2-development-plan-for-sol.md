# RTMP Stream Monitor 2.0 — план розробки для Sol

Статус: продуктове й технічне завдання. Поточна версія продовжує працювати; цей документ задає напрям переробки. Мова інтерфейсу за замовчуванням — українська, з можливістю англійської локалізації. Ціль — система для роботи 24/7; не витрачати етапи на окремий demo або макет із синтетичними даними.

## 1. Який результат потрібен користувачу

Адміністратор відкриває потік і за кілька секунд бачить **коли саме** просів бітрейт, **на якому пункті спостереження** це сталося і **які помилки** з'явилися в той самий час. Натискання на подію відкриває зрозуміле пояснення з числовими доказами, порівнянням сусідніх probe і рівнем упевненості. Додати клієнта можна з панелі без ручного редагування YAML, а центральний сервер запускається через Docker Compose.

Це продукт для швидкої відповіді на запитання «що сталося з моїм потоком?». Графік потоку з помилками на спільній часовій шкалі — головний екран і основний спосіб діагностики; адміністративні таблиці та сирі метрики — допоміжні.

Типовий сценарій: Ubuntu-сервер приймає/роздає RTMP через інший застосунок; наш monitor спостерігає за виходом сервера та Windows/Ubuntu-клієнтами, не керує самим стрімом і не перериває його.

Критерій користувацької цінності: на одній часовій шкалі видно лінії виміряного бітрейту та маркери freeze, втрат кадрів, помилок декодування, проблем PTS/ключових кадрів, перепідключень і недоступності probe. Відсутність даних показується прогалиною, а не нулем.

## 2. Від чого відштовхнутися в репозиторії

- Зберегти наявну модель центрального сервера, ролі `SOURCE`, `SERVER_INGRESS`, `SERVER_EGRESS`, `CLIENT`, збір телеметрії, локальну чергу агента, часові позначки, кореляцію інцидентів і наявні агентські API там, де вони придатні. Не переписувати робочу частину лише заради нової структури папок.
- Поточний `src/rtmp_monitor/static/index.html` — один великий файл із вбудованими стилями, логікою та canvas timeline. Замінити його на підтримуваний фронтенд із компонентами, окремими стилями та станом даних. Запропонований стек: React + TypeScript + Apache ECharts; production build віддає FastAPI, тому Node.js потрібен тільки під час збірки, не на сервері користувача.
- У `src/rtmp_monitor/agent.py` режим `LIGHT` оцінює бітрейт за розмірами пакетів `ffprobe`, а `DEEP` використовує поле бітрейту з `FFmpeg -progress`. Останнє не гарантує виміру вхідного RTMP-потоку й уже дає `N/A`. **Це блокер для графіка.** Спершу Sol має визначити й реалізувати один чітко названий вимір прийнятих медіаданих в обох режимах.
- `/api/v1/timeline` і поточні агрегації можна використати як основу, але графіку потрібні спеціальні запити для часових рядів, збереження коротких провалів і відокремлення подій від метрик. Зберегти сумісність ingest API зі старими агентами на час переходу.
- Linux-інсталятор тепер підтримує Python 3.10+, тож Ubuntu 22.04 сумісна без заміни системного Python. Windows поки потребує Python 3.12+ та FFmpeg і не має self-contained пакета; це одна з головних проблем продукту. Історичну базу та токени на чинному Ubuntu-сервері треба перенести без втрати інцидентів.

## 3. Інформаційна структура й напрям дизайну

### Принципи інтерфейсу

- Починати з потоків і їхнього стану, а не з інвентарю серверів чи загального переліку алертів. На картці потоку показувати LIVE/OFFLINE/UNKNOWN, короткий графік бітрейту за останні 15 хвилин, підключені клієнти та останню важливу подію.
- Деталі одного потоку зібрати в одному робочому просторі: вибір інтервалу, графік усіх пунктів, доріжки подій і пояснення відкриваються без переходів між окремими сторінками.
- Візуально відділяти головне від діагностичних подробиць. За замовчуванням показувати бітрейт, свіжість вимірів і важливі події; CPU, RAM, мережеві лічильники, сирі payload-и та службові дії відкривати за потреби.
- Використовувати короткі українські назви та пояснення. Технічний код події можна показати в розгорнутих деталях, але він не замінює людський опис.
- Тримати навігацію компактною: «Потоки», «Клієнти», «Налаштування». Історія інцидентів доступна в контексті потоку та через пошук, але не витісняє графік з головного сценарію.
- Майстер клієнта має вести від вибору потоку та ролі до команди встановлення, а потім показати стан підключення й наступну дію. Довгі токени й YAML не є частиною звичайного сценарію.

Орієнтовний сценарій приймання інтерфейсу: оператор відкриває картку `poland`, бачить падіння бітрейту біля 07:25, натискає на маркер `CLIENT_PROBLEM`, порівнює server egress з `predator`, читає які метрики підтверджують або не підтверджують мережеву причину, і з панелі клієнтів створює команду підключення ще одного probe. Сирий код `CLIENT_PROBLEM` сам собою не є відповіддю: пояснення має назвати симптом, місце спостереження, факти та те, чого телеметрія не доводить.

### Сторінка «Потоки»

Короткий список/картки потоків: назва, LIVE/OFFLINE/UNKNOWN, кількість підключених пунктів, останній інцидент і час. Звідси можна створити потік, змінити його URL і перейти до детального перегляду. Статус `UNKNOWN` не маскувати під справний стан.

### Сторінка потоку — головний екран

1. Шапка: назва, статус, актуальність даних, вибір 15 хв / 1 год / 6 год / 24 год / 7 днів / довільного інтервалу, `Live` і пауза, таймзона.
2. **Головний графік:** X — спільний час; Y — Mbps; окрема лінія для кожного probe, чіткі назви та постійні кольори. Наведення показує точний час, probe, значення, вік даних і спосіб виміру. Можна приховати/показати лінії, масштабувати та прокручувати.
3. **Доріжки подій безпосередньо під графіком:** окремо source/server/client; маркери за типом і серйозністю; збіг із провалом бітрейту видно без переходу на іншу сторінку. Клацання відкриває картку інциденту і підсвічує інтервал на графіку. Довгі події — інтервалом, точкові — маркером.
4. Синхронізовані допоміжні графіки: інтервал ключових кадрів/GOP, декодовані кадри/FPS, TCP retransmits/RTT там, де ці лічильники реально доступні. Не змішувати різні одиниці на одній осі без чіткого позначення.
5. Порівняння пунктів на вибраному інтервалі: source → server ingress → server egress → client. Кожний пункт показує роль, URL/місце, режим і свіжість телеметрії. Якщо справжнього ingress probe немає, пояснення причини не повинно заявляти про підтверджену проблему джерела.
6. Панель інциденту: «Що сталося», «Де помітно», «Що підтверджують метрики», «Що ще невідомо», імовірна зона проблеми й упевненість. Людське пояснення формується спочатку з перевірених правил; OpenAI API може бути опційним шаром перефразування, без вигадування фактів.

Список інцидентів залишається для пошуку та фільтрації, але основний спосіб дослідження — графік. `NaNs` у тривалості, сирі коди на кшталт `CLIENT_PROBLEM` і технічні повідомлення без пояснення не потрапляють у головний вигляд.

### Сторінка «Пункти спостереження»

Майстер додавання: вибрати потік, роль і ОС → створити короткочасний одноразовий код підключення → отримати відповідний інсталятор або одну команду → бачити `очікує / підключається / працює / помилка` з діагностикою. URL потоку, центрального сервера й роль агент отримує після реєстрації; користувач не переписує YAML і довгі токени. Тут же: пауза, зміна ролі/потоку, відкликання доступу, видалення. Стара історія вимірів не повинна зникати автоматично після видалення клієнта.

## 4. Контракт метрик і часових даних

Перед написанням графіка Sol робить короткий вимірювальний spike на реальному 1080p/50 fps RTMP-потоці:

- Визначити `received_media_bitrate_bps`: бітрейт за прийнятими медіабайтами за явно визначене вікно, наприклад 1 с для live та 5 с для огляду; позначити, які байти входять до виміру. Не називати його мережевою пропускною здатністю з урахуванням усіх протокольних накладних витрат.
- Забезпечити вимір у `LIGHT` і `DEEP`. Якщо `DEEP` потребує другого читача або іншого способу читання, виміряти додаткове навантаження на CPU, RAM і мережу, описати рішення і дати налаштування для ресурсообмеженого сервера. Не малювати метадані кодека або вихідний бітрейт FFmpeg як фактичний вхідний бітрейт.
- Кожен запис має `observed_at` у UTC, ідентифікатори stream/probe, роль, режим, значення, одиницю, довжину вікна, sample count і якість/причину відсутності даних. Зберігати час отримання сервером та оцінку розбіжності годинників окремо.
- На великих інтервалах API повертає для кожного бакета `min/avg/max` та кількість вимірів, щоб короткий провал залишався видимим після зменшення деталізації. За сильного збільшення показувати початкові 1-секундні точки. Пропуск телеметрії, `0 bps` і агент offline — три різні стани.
- Події містять фактичні `started_at/ended_at`, probe, тип, серйозність, симптоми, докази та статус. API повертає часові ряди й події для одного інтервалу; межі, UTC і часове вирівнювання визначені однозначно. Бажаний контракт — версовані `/api/v2/streams/{id}/series` та `/api/v2/streams/{id}/events`; точні DTO зафіксувати до реалізації фронтенду.
- У live режимі нові точки й події з'являються без ручного перезавантаження. Обрати SSE або інкрементальний polling і перевірити відновлення після втрати зв'язку та захист від дубльованих подій у інтегрованому dashboard/API на production-потоці.

## 5. Розгортання й оновлення

### Центральний сервер

Підготувати versioned Docker image та `compose.yaml` для одного Ubuntu-хоста: застосунок, healthcheck, restart policy, постійний volume для бази/налаштувань, параметри URL/TLS/секретів через setup wizard або `.env`. Під час першого входу wizard створює обліковий запис адміністратора; панель не відкривається без авторизації. Для першого релізу допустима SQLite з індексами й агрегатами, якщо навантажувальний тест підтвердить сценарій кількох потоків і десятків probe. Перехід на PostgreSQL — лише за чітким критерієм продуктивності; це не повинно ускладнювати базову інсталяцію. Опублікувати версований образ і зрозумілу інструкцію: встановити Docker, скопіювати один `compose.yaml`, виконати `docker compose up -d`, відкрити setup wizard.

Окремо вирішити, як server-local probe дістається до RTMP/SRS на цьому самому хості. Контейнер не має автоматично доступу до host loopback. Перевірити host networking або залишити невеликий нативний агент із таким самим майстром реєстрації. Не блокувати запуск центрального сервера на відсутності server-local probe.

Забезпечити резервну копію, відновлення, оновлення образу й rollback. Міграція наявної `central.db` повинна зберегти потоки, probe, інциденти та вимірювання, а старі агенти — продовжувати надсилати дані під час переходу. Записати явний сценарій переходу з поточної systemd-інсталяції на Compose.

### Клієнтські агенти

- Windows: версований MSI/EXE, що містить потрібний Python runtime і сумісні FFmpeg/ffprobe або інший обґрунтований runtime; встановлює Windows Service без окремого Python, `pip` і ручної правки PATH. Перевірити ліцензійні умови обраної збірки FFmpeg для розповсюдження. Публікувати контрольну суму; цифровий підпис додати, коли буде сертифікат. Включити ремонт, оновлення, видалення й діагностичний log viewer/команду. Не вимагати Docker Desktop на клієнті.
- Ubuntu: `.deb` або одна команда завантаження перевіреного пакета + systemd. Майстер дає код/команду й показує стан реєстрації. Якщо використовується FFmpeg із системного репозиторію, інсталятор перевіряє його сам і видає конкретну помилку.
- Одноразовий enrollment code має короткий термін життя і права лише на реєстрацію конкретного probe. Подальший агентський токен можна відкликати з UI. Для віддалених клієнтів потрібен HTTPS/TLS; секрети не потрапляють у Git чи звичайні журнали.

Docker Compose для центрального сервера спирається на [production-рекомендації Docker](https://docs.docker.com/compose/how-tos/production/), [named volumes](https://docs.docker.com/reference/compose-file/volumes/) і [secrets](https://docs.docker.com/reference/compose-file/secrets/). ECharts обрано для часової осі, zoom і кліків по подіях: [axis](https://echarts.apache.org/handbook/en/concepts/axis/), [events](https://echarts.apache.org/handbook/en/concepts/event/). Перевіряти його слід як частину живої панелі на API-контракті й реальних telemetry samples, без окремого UI demo.

## 6. Етапи для Sol і критерії приймання

### M0 — виробнича технічна перевірка — виконано

Не будувати окремий demo чи UI на синтетичних даних. Перевірити на реальному RTMP-потоці, звідки обидва профілі беруть виміряний бітрейт, keyframe/GOP метадані та часові позначки; заміряти накладні витрати й записати обмеження для SRS ingress, server egress та клієнтського probe. Зафіксувати DTO для series/events, часову семантику, якість/прогалини даних і версійність API. Далі реалізовувати наскрізні виробничі вертикальні зрізи: збір → збереження → API → реальний dashboard, а не презентаційні заглушки.

**Приймання:** метод вимірювання перевірений на реальному потоці в `LIGHT` і `DEEP`; короткий bitrate drop та реальна помилка відтворюються в записаній телеметрії; CPU/RAM/мережеве навантаження задокументовані; контракти не плутають нуль, відсутні дані й offline. Існуючий макет [stream-detail-v2.html](prototype/stream-detail-v2.html) містить синтетичні дані й не є частиною продукту; не розвивати його.

Артефакти M0: [контракт API](v2-series-events-contract.md), [звіт вимірювального spike](v2-bitrate-spike.md), результати runtime-вимірів і відтворювані fixtures для automated tests.

**Виконання:** обидва профілі вимірюють бітрейт із медіапакетів; live RTMP та контрольований короткий bitrate dip/freeze пройшли крізь агент, збереження й API. CPU/RAM заміри та межі однієї спільної мережі задокументовано. Контракт розрізняє виміряний нуль, відсутню секунду та offline; fixtures відтворюють провал і медіаподію. Артефакти та перевірки — у звітах M1 і M6 та двох документах, перелічених вище.

### M1 — надійна телеметрія й API — виконано

Реалізувати однакову семантику виміряного бітрейту для обох режимів, зберігання UTC/якості, min/avg/max агрегації, індекси й версовані API. Історичні записи без бітрейту лишаються прогалинами. **Приймання:** на 1-годинному графіку штучно створений короткий провал видно; немає фальшивого нуля/інтерполяції; старий агентський ingest працює.

**Виконання:** M1 реалізовано; деталі та обмеження — у [звіті M1](m1-telemetry-api.md). Одногодинний API-тест зберігає п'ятисекундний спад у `min_bps`, відрізняє нуль від прогалин, retention зберігає виміряні хвилинні агрегати, `/api/v1/ingest` лишився сумісним. Повний тестовий набір пройшов на Windows/Python 3.12 та Ubuntu 22.04 контейнері/Python 3.10 (`113 passed, 1 skipped`); системний FFmpeg 4.4.2 у Jammy контейнері пройшов live і контрольований SRS smoke в обох профілях. Фізичний Linux target і PostgreSQL потребують окремого runtime-прогону.

### M2 — новий головний екран — частково виконано

Винести фронтенд у окремий проєкт і реалізувати сторінки «Потоки», «Потік», «Клієнти». Візуальна ієрархія має вести до стану потоку та його графіка, а не до щільної таблиці хостів/алертів. Графік має лінії probe, спільні часові доріжки подій, інтервали, zoom, tooltips, live update, порівняння точок і адаптацію до ширини екрана. **Приймання:** оператор за кілька кліків знаходить конкретний провал і пов'язану подію; тестовий сценарій із `poland` та `predator` проходиться від картки потоку до пояснення і створення нового клієнта; 24 год / 4 probe відкриваються без зависання, 7 днів використовують агрегати.

**Виконання:** інтегрований React/TypeScript dashboard замінив стару односторінкову панель. Доступні сторінки потоків, деталей потоку, пунктів спостереження та інцидентів; графік звертається до реальних `/api/v2/streams/{id}/series` і `/events`, показує окрему виміряну лінію кожного probe, min/max-діапазон для коротких спадів, прогалини без текстового перекриття, zoom, перемикачі періоду, live polling і спільні доріжки подій. Маркер відкриває пояснення з доказами й обмеженням висновку. Enrollment wizard видає одноразовий код і команду інсталяції, а revoke зберігає історію. FastAPI віддає production assets; CI перевіряє typecheck і production build. Базову оболонку та форми перевірено в браузері на чистій локальній БД. Графік перевірено на реальному потоці через одночасні Windows CLIENT probes у профілях LIGHT і DEEP: API повернув виміряні 1-секундні buckets, а кореляція не приписала причину без upstream/egress доказів. Контрольований SRS/FFmpeg сценарій перевірив у production dashboard обидві лінії, шестисекундний bitrate dip, FREEZE_START/END і картку з числовими доказами та `UNCONFIRMED`. Вікна 24 год/4 probe й 7 днів перевірені на API та UI fixtures з виміряним часом і розміром відповіді; деталі збережені нижче й у [M6 live validation](m6-live-validation.md). 30.09.2026 новий 30-секундний read-only capture з наданого RTMP URL підтвердив live measured series: 24 секунди для LIGHT і 25 для DEEP, середні `8.087` та `8.364 Mbps`; подій у цьому вікні не було. Smoke-скрипти — [live-multiprobe-smoke.py](../scripts/live-multiprobe-smoke.py) і [benchmark-series-load.py](../scripts/benchmark-series-load.py).

**Додаткова перевірка M3 (30.09.2026):** знайшов неузгодженість, де корелятор відкидав прострочені мережеві counters, а пояснення ще могло показати їх як актуальний доказ або «чистий» TCP sample. Спільний helper тепер застосовує однаковий поріг свіжості; застарілі значення виключаються з локалізації й картка пояснює, чому. ### M6 — наскрізна перевірка й випуск — частково виконано

Перевірити на реальному RTMP сервері з локальним server egress і щонайменше двома клієнтськими probe (Windows та Ubuntu, якщо доступні), включно з перепідключенням, просіданням бітрейту, freeze, помилкою декодування, втратами телеметрії, зсувом годинника, рестартом і оновленням. Додати автоматичні перевірки агрегацій/API/UI/інсталяторів і коротку операторську інструкцію. **Приймання:** графік і події збігаються за часом; встановлення/оновлення/видалення відтворювані; система не приписує доведену причину без належних доказів.

**Виконано локально:**

- [x] Windows і Ubuntu 22.04/Python 3.10/FFmpeg 4.4.2 прогони виміряли live RTMP у `LIGHT` і `DEEP`; Ubuntu повернув 28/26 measured buckets. Зафіксовано реальний `PTS_REGRESSION`, але його причину не локалізовано.
- [x] Локальний SRS/FFmpeg fixture перевірив bitrate dip і freeze в обох профілях; Windows dashboard показав обидві лінії, спільну шкалу подій і картку з тривалістю 6.02 s та `UNCONFIRMED` висновком.
- [x] Ізольований рестарт SRS та 10-секундний GOP дали `FFMPEG_RESTART`, `KEYFRAME_GAP` і `KEYFRAME_GAP_END`; агенти відновили вимірювання.
- [x] **Client-only TCP outage:** proxy клієнтів вимикався на 8 s, тоді як прямий `SERVER_EGRESS` мав 8 виміряних бакетів (середнє 0.994 Mbps); обидва клієнти перепідключилися, а корелятор створив `NETWORK_PATH_PROBLEM` між server egress і клієнтами.
- [x] **Bitstream corruption/decode recovery:** локальний SRS сценарій тричі записав `DECODE_ERROR` на `DEEP`; до рестарту сервера декодер відновив кадри (`last_frame_age` 0.110–0.187 s), а після рестарту `LIGHT` і `DEEP` знову мали виміряний бітрейт. Повідомлення `ffprobe` від `LIGHT` окремо класифікується як `BITSTREAM_PARSE_ERROR`.
- [x] **Втрата IP-пакетів на клієнтському RTMP-шляху:** два прогони з `tc netem loss 20%` підтвердили drops/відновлення без діагнозу; три з 50% loss зафіксували `NETWORK_PATH_PROBLEM` через PTS lag 11.251 s, 10.581 s і 6.691 s при здоровому `SERVER_EGRESS`. Цей діагноз тепер вимагає, щоб обидва виміри були профілю `LIGHT` і отримані не далі один від одного за медіатолерантність; пояснення явно називає PTS lag ознакою відставання, а не доказом packet loss. Усі попередні події мали `UNCONFIRMED`; Monitor не вимірював фактичний packet-loss rate і не доводив механізм.
- [x] Додано Windows receiver TCP EStats для IPv4 RTMP-з'єднання, прив'язаного до PID процесу probe, з інтервальними `duplicate ACK episodes`; кореляція використовує лічильник лише разом із поточним client media symptom. Unit тести перевіряють відбір PID/адреси/порту, базовий sample після перепідключення, статус помилки прав і людське пояснення, що сегменти могли бути пропущені або переставлені. Реальний виклик з інтерактивного неадміністративного процесу повернув `PERMISSION_DENIED`, як очікує API; робота від імені LocalSystem service та вимірювання packet-loss сценарію ще не перевірені.
- [x] GitHub Actions run [36661346435](https://github.com/Sadoharu/rtmp-stream-monitor/actions/runs/36661346435) виконав нативний Windows TCP EStats loopback smoke від імені `LocalSystem` на Python 3.12, 3.13 і 3.14. Це перевіряє доступність API в контексті облікового запису служби, але ще не вимірювання на реальному RTMP-з'єднанні встановленої служби.

**Ще відкрите; M6 лишається частковим:**

- [ ] Перевірити в браузері live-графік потоку `poland`. Попередні live-запуски доводять тільки API series; контрольний dashboard перевірявся на локальному SRS fixture.
- [ ] Перевірити на фізично незалежних хостах: `SERVER_EGRESS` та клієнти з інших Windows/Ubuntu мереж. Loopback сценарії цього не підтверджують.
- [x] Повторно відтворити пошкодження H.264-пакетів, `DECODE_ERROR` у `DEEP` і відновлення декодування/бітрейту; деталі й команда — у звіті M6.
- [ ] Перевірити діагностику на Windows з реальною службою LocalSystem та незалежними production-подібними probe й нижчими рівнями втрат: локально `tc netem` 50% дав `NETWORK_PATH_PROBLEM`; після часового фільтра два прогони на 20% дали змішаний результат — один без діагнозу при 240 drops, інший з `UNCONFIRMED` за PTS lag 5.731 s при 211 drops. На 10% було 53 drops без мережевого діагнозу чи підтвердженої медіапроблеми. Windows EStats поки перевірено на loopback від імені `LocalSystem`, але ще не на реальному RTMP loss/reorder; вони підтримують IPv4 і вказують на пропущені або переставлені сегменти, але не вимірюють відсоток втрат. Повторюваність і межа чутливості не визначені; bitstream corruption не є network packet loss.
- [ ] Перевірити цільові production install/upgrade, міграцію Ubuntu systemd бази та rollback. GitHub Actions Ubuntu 22.04 уже перевіряє пакетний install/upgrade/purge на чистому runner, але це не перевіряє міграцію існуючої бази та rollback на production-сервері.

Деталі — у [M6 live validation](m6-live-validation.md).

## 7. Загальні критерії готовності

1. У `DEEP` і `LIGHT` є фактично виміряний вхідний бітрейт з документованою методикою, або UI чесно показує причину, чому його немає.
2. П'ятисекундний провал не губиться при перегляді 24 годин; перехід до детального інтервалу показує сирі точки й точний час події.
3. Графік чітко розрізняє server egress та кожного клієнта; порівняння не приховує offline probe і часову неузгодженість.
4. Оператор може встановити, оновити, діагностувати та видалити probe з документованим способом; Windows не вимагає ручного Python/FFmpeg/PATH.
5. Центральний сервер запускається з Compose, має перевірку здоров'я, persistent data, backup/restore, безпечне оновлення й перевірений шлях міграції поточного інстансу.
6. Пояснення інцидентів посилаються на конкретні виміри, а рівень упевненості відповідає наявності source/ingress/egress/client probe.

Продовжуй із першого незакритого критерію та розробляй V2 як production-систему для безперервної роботи 24/7. Це має бути зручний інструмент для відповіді «що сталося з моїм потоком?»: головний екран — графік бітрейту кількох probe з помилками на спільній часовій шкалі, а не щільна інфраструктурна таблиця чи загальний список кодів тривог. Пріоритети: фактично виміряний бітрейт у DEEP/LIGHT, зрозумілі пояснення з числовими доказами й чесно позначеною невизначеністю, Docker Compose для центрального сервера та просте додавання/керування Windows/Ubuntu-клієнтами без ручного Python/YAML. Для UI використовуй потік `poland` і сценарій із `predator` як наскрізний приклад, коли доступний відповідний RTMP target; не вигадуй результати, якщо target недоступний. Зберігай історію й сумісність чинних агентів під час міграції. Доводь кожний етап до критеріїв приймання, фіксуй рішення та відомі обмеження і перевіряй реальні сценарії. Не підмінюй виміряний бітрейт метаданими чи FFmpeg output bitrate і не стверджуй кореневу причину, якщо бракує probe. Після кожного етапу повідомляй, що готово, як перевірено і що лишилося.

План побудовано як послідовність етапів із критеріями приймання за [рекомендаціями OpenAI для тривалих задач Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex). Модель [GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol) придатна для цієї кодової задачі; кінцеві архітектурні рішення слід підтверджувати вимірами й інтегрованим приймальним тестом.
